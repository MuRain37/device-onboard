# 设备接入 MVP 规格

Status: ready-for-agent

## Problem Statement

用户需要在多台 macOS 设备上使用同一台服务器上的 AI harness、skills 和项目环境。当前每台设备都要重复配置 SSH 密钥、服务器授权、反向隧道、SSH Host 和设备记录，容易出错，也难以维护。

用户希望设备保持轻量，只提供终端入口；服务器作为 AI 中心节点，集中运行 Codex CLI、Claude Code 或其他 Harness。设备接入后，用户可以从设备登录服务器、启动服务器到设备的反向 SSH 通道，并直接在服务器上启动 Harness。

## Solution

提供一个面向 macOS 的 POSIX shell MVP。用户首次运行 `install.sh`，脚本先安装本地命令，再直接进入设备接入流程。接入流程收集设备名、服务器地址、服务器用户和服务器 SSH 端口，使用系统 SSH 完成主机指纹确认、密码提示或现有密钥认证。

脚本生成设备到服务器的专用密钥，并把设备公钥加入服务器；服务器生成独立的回连设备密钥，脚本把其公钥加入设备的 SSH 授权文件。脚本自动选择反向隧道端口，维护双方 `~/.ssh/config` 的自有标记区块，并在服务器的 canonical skill 中登记设备信息。

接入完成后，用户通过三个独立入口工作：普通 SSH Host 进入服务器 shell，`device-tunnel` 前台启动反向 SSH 隧道，用 `ssh onboard-server-<设备名> <command>` 在服务器上启动指定 Harness（`device-harness` 则一键把隧道与 Harness 绑成同生共死的一条命令）。安装脚本重跑时更新本地命令；已有设备配置存在时跳过首次接入。

## User Stories

1. 作为设备使用者，我希望首次运行一个安装脚本就进入接入流程，从而不必手工执行多条初始化命令。
2. 作为设备使用者，我希望输入服务器地址、用户和端口，从而连接局域网、公网或 VPN 中可达的服务器。
3. 作为设备使用者，我希望设备名默认取 macOS 主机名，从而减少输入；同时可以手动修改名称。
4. 作为设备使用者，我希望系统 SSH 自己显示服务器主机指纹，从而确认服务器身份。
5. 作为设备使用者，我希望已有 SSH key 或 SSH agent 时直接免密连接服务器。
6. 作为设备使用者，我希望没有可用密钥时由系统 SSH 提示密码，而不是由工具读取或保存密码。
7. 作为设备使用者，我希望工具为当前设备与当前服务器生成独立的设备密钥，从而避免复用默认身份并便于撤销。
8. 作为设备使用者，我希望设备私钥只保存在设备上，从而避免私钥进入服务器档案或日志。
9. 作为设备使用者，我希望服务器生成独立的回连设备密钥，从而把两个方向的访问权限分开。
10. 作为设备使用者，我希望服务器回连公钥自动安装到设备，从而不必手工复制公钥。
11. 作为设备使用者，我希望反向端口由服务器自动选择，从而不必手工记录和解决端口冲突。
12. 作为设备使用者，我希望工具在接入前检查 macOS 的 SSH 工具和本地目录，从而在缺少前置条件时得到明确错误。
13. 作为设备使用者，我希望工具检查设备 SSH 服务是否可用，从而避免配置出无法回连的设备。
14. 作为设备使用者，我希望工具只修改自己的 SSH 配置区块，从而保留已有的 `~/.ssh/config` 内容。
15. 作为设备使用者，我希望工具在修改 SSH 配置前创建备份，从而能恢复本次改动。
16. 作为设备使用者，我希望普通服务器连接和反向隧道分别有清晰的 SSH Host，从而可以独立使用它们。
17. 作为设备使用者，我希望服务器侧有一个回连设备的 SSH Host，从而服务器可以通过反向隧道访问设备。
18. 作为设备使用者，我希望设备记录集中在服务器的 canonical skill 中，从而其他 Harness 可以复用同一份信息。
19. 作为 Harness 使用者，我希望 canonical skill 放在 `.agents/skills` 的标准 skill 目录结构中，从而符合现有 Harness 的发现方式。
20. 作为 Harness 使用者，我希望其他 Harness 可以通过软链接复用 canonical skill，从而不维护多份设备记录。
21. 作为设备使用者，我希望首次接入完成后自动进行设备到服务器的端到端验证，从而确认正向连接真正可用。
22. 作为设备使用者，我希望在启动临时反向隧道后自动进行服务器到设备的端到端验证，从而确认转发链路真正可用。
23. 作为设备使用者，我希望反向隧道验证结束后临时隧道自动关闭，从而首次配置不会留下未知的常驻进程。
24. 作为设备使用者，我希望验证失败时看到失败方向和原因，从而知道是设备登录、服务器登录还是反向转发出错。
25. 作为设备使用者，我希望验证失败时清理本次新增的授权、配置区块、设备记录和密钥，从而不留下半完成状态。
26. 作为设备使用者，我希望同名设备只有在身份匹配时才允许覆盖，从而避免误覆盖另一台设备。
27. 作为设备使用者，我希望安装脚本重跑时只更新本地命令并保留已有接入配置，从而可以安全升级工具。
28. 作为设备使用者，我希望用普通 SSH Host 进入服务器交互式 shell，从而处理不属于 Harness 的任务。
29. 作为设备使用者，我希望用 `device-tunnel` 在前台启动反向 SSH 隧道，从而能看到错误并用 `Ctrl-C` 结束连接。
30. 作为设备使用者，我希望反向端口被占用时隧道命令立即失败，从而不会误以为连接已经建立。
31. 作为设备使用者，我希望用 `ssh onboard-server-<设备名> <command>` 启动服务器上的 Harness，从而不必先登录服务器再手工输入命令。
32. 作为设备使用者，我希望 Harness 命令通过普通服务器 Host 执行，而不是为每个 Harness 生成 SSH Host，从而保持 SSH 配置简单。
33. 作为设备使用者，我希望 SSH 断开时远程 Harness 进程结束，从而首版不留下后台任务。
34. 作为维护者，我希望首版只支持 macOS，从而先验证接入链路，不被 Linux、Termux 和系统服务差异拖慢。
35. 作为维护者，我希望所有关键流程都能在隔离临时 HOME 中测试，从而不会污染开发者真实 SSH 配置。

## Implementation Decisions

- 实现形态是一个设备侧 POSIX shell 项目，首版目标平台为 macOS。
- `install.sh` 是用户首次运行的入口：安装本地命令后直接进入接入向导；再次运行时更新本地命令，已有设备档案则跳过接入。
- 安装脚本不依赖包管理器，不要求设备预先 clone 项目以外的运行时依赖。
- 本地命令分为安装/接入入口、反向隧道命令和远程 Harness 启动命令。反向隧道命令独立于安装命令，并以前台运行。
- 使用系统 `ssh`、`ssh-keygen` 和 SSH agent；工具不实现密码捕获、密码存储、`sshpass` 或 `expect`。
- 使用 SSH 的首次主机指纹确认流程，不关闭主机密钥校验。
- 设备密钥和服务器回连密钥分开生成；私钥不写入 canonical skill。
- 设备密钥和服务器回连密钥放在各自的工具专用 SSH 目录中，SSH 配置通过 `IdentityFile` 引用逻辑密钥。
- 设备侧配置普通服务器 Host 和反向隧道 Host；服务器侧配置通过 `127.0.0.1:<reverse-port>` 回连设备的 Host。
- Host 名称使用固定工具前缀和设备名，避免覆盖用户已有 Host；脚本只修改自己的标记区块。
- 修改 SSH 配置和设备档案前创建备份；写入失败或验证失败时恢复本次备份并清理新增授权。
- canonical skill 位于服务器用户的 `.agents/skills/device-onboard/SKILL.md`，设备记录嵌入机器可读标记区块；其他 Harness 通过软链接复用该 skill。
- 设备记录只保存重建配置需要的最小字段：设备名、服务器地址、服务器用户、服务器 SSH 端口、设备 SSH 端口、反向端口、设备密钥名和服务器回连密钥名。
- 设备接入过程中服务器自动选择配置端口范围内的空闲反向端口；设备用户不输入反向端口。
- 接入流程需要设备的 macOS SSH 服务可用，因为服务器回连必须经过设备主动建立的反向隧道。
- 接入流程使用一个临时前台反向隧道完成端到端验证；验证完成后关闭，不提供后台保活。
- 日常 `device-tunnel` 命令以前台运行反向隧道，端口转发失败时立即退出，用户用 `Ctrl-C` 结束。
- 日常用 `ssh onboard-server-<设备名> <command>` 复用普通服务器 Host，通过交互式 SSH 在服务器执行远程 Harness 命令；`device-harness` 则一键编排（起反向隧道 + 跑 harness，同生共死）。
- 首版不维护 Harness 注册表；命令由用户通过 `ssh onboard-server-<设备名> <command>` 传入，工作目录通过命令参数或远程 shell 处理。
- 同名设备只有在已有身份与当前 SSH 主机指纹或接入密钥一致时才允许覆盖，否则停止并报告冲突。
- 服务器只需要普通 SSH 用户权限；首版不修改系统级 sshd、防火墙或服务配置。

## Testing Decisions

- 测试最高层的命令行工作流和文件/SSH 外部行为，不测试 shell 函数内部实现细节。
- 测试使用隔离临时 HOME，替换 `HOME`、SSH 配置目录和工具密钥目录，禁止写入真实用户的 SSH 文件。
- 测试使用可控的本地 SSH 环境或测试替身，覆盖首次主机指纹确认、密码/密钥认证、公钥安装、反向转发和服务器回连。
- 安装测试覆盖首次运行：本地命令安装、接入提示、设备档案写入、双方 SSH Host 写入和日常命令输出。
- 重跑测试覆盖已有设备档案：本地命令更新，不重复生成或覆盖匹配的接入资料。
- 配置测试覆盖工具标记区块的幂等更新，确认用户已有 SSH 配置内容保持不变。
- 验证测试覆盖正向登录成功、反向隧道成功、端口占用、服务器回连失败和 SSH 服务不可用。
- 回滚测试覆盖接入步骤任意阶段失败时，新增授权、密钥引用、SSH 配置区块和 skill 记录均被清理或恢复。
- Harness 测试只验证远程命令参数被正确传递，并确认使用交互式 SSH；不测试具体 Codex 或 Claude 实现。
- 当前仓库没有既有测试先例，因此测试基础设施应围绕命令行黑盒测试和本地 SSH fixture 建立。

## Out of Scope

- Linux、Termux 或其他设备平台的完整支持。
- 多设备协同、共享工作区、任务分发、Git worktree 管理和自动合并。
- 后台隧道、自动重连、系统服务、自启动和唤醒锁保活。
- 服务器 API、常驻 agent、远程管理 daemon 或系统级 sudo 配置。
- 多 Harness 注册表、Harness 专属 SSH Host 和复杂命令发现机制。
- 密码保存、自动绕过主机指纹确认、`sshpass` 或 `expect`。
- 在线状态、最后在线时间和其他易变运行时信息写入 skill。
- 复杂版本迁移、端口回收策略和跨服务器的集中管理
## Further Notes

- 本规格以服务器作为 AI 中心节点的 ADR 和项目 `CONTEXT.md` 术语为准。
- `device-tunnel` 的交互行为参考现有本机 tunnel 命令：前台运行、转发失败立即报告、用户用 `Ctrl-C` 结束。
- 规格完成后，下一步可以用 `/to-tickets` 把安装入口、SSH 配置、密钥交换、反向隧道、Harness 命令和黑盒测试拆成实现票据。
